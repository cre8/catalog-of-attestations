## 1 Introduction

### 1.1 Document scope and purpose

This Attestation Rulebook defines the `Gym Membership Card` attestation type.

The purpose of this attestation is to provide a verifiable digital credential that proves an individual's membership status at a fitness facility. It enables gym members to digitally prove their membership for access control, membership-tier benefits, and discounts at partner facilities.

This attestation is designed as a **non-qualified Electronic Attestation of Attributes (non-qualified EAA)** for use within the EUDI Wallet ecosystem.

This Rulebook is provided as a **non-normative example** for authors of attestation rulebooks. It demonstrates how a simple, sector-specific, non-qualified EAA can be described using the EUDI Wallet Attestation Rulebook template. The example issuer names, domains, trust-list URLs, identifiers, and values in this document are illustrative and SHALL NOT be used as production trust anchors.

The design intentionally keeps the attestation simple:

* the attestation is encoded as an SD-JWT VC;
* the attestation is device-bound to the Wallet Unit key;
* the attestation is not cryptographically bound to a PID by default;
* the attestation is intended for online presentation;
* revocation is supported by a status claim;
* trust anchors are resolved from the attestation catalogue / attestation definition, not solely from data contained in the presented credential.

### 1.2 Document structure

This Rulebook is structured as follows:

* **Chapter 2** describes the attestation attributes and metadata in an encoding-independent manner.
* **Chapter 3** specifies how the attestation attributes and metadata are encoded as an SD-JWT VC.
* **Chapter 4** specifies attestation usage, including relying-party obligations and device-binding requirements.
* **Chapter 5** defines how trust anchors for attestation verification can be obtained.
* **Chapter 6** defines attestation revocation mechanisms.
* **Chapter 7** provides compliance information.
* **Chapter 8** provides references.

### 1.3 Key words

This document uses the capitalised key words `SHALL`, `SHOULD`, and `MAY` as specified in [RFC 2119], i.e., to indicate requirements, recommendations, and options specified in this document.

In addition, `must` is used to indicate an external constraint, i.e., a requirement that is not mandated by this document, but, for instance, by an external document. The word `can` indicates a capability, whereas other words such as `will`, `is`, or `are` are intended as statements of fact.

### 1.4 Terminology

This document uses the terminology specified in Annex 1 of the Architecture and Reference Framework (ARF).

## 2 Attestation attributes and metadata

### 2.1 Introduction

This chapter defines all attributes and metadata that an attestation of type `Gym Membership Card` may contain. Attributes and metadata are defined in an encoding-independent manner.

This attestation is a **non-qualified EAA**. According to ARB_12 in [Topic 12], an indication that the attestation is an EAA SHOULD be included. This Rulebook therefore defines the attribute `attestation_legal_category`, which SHALL have the value `non-qualified-EAA`.

Unless otherwise stated, all string attributes SHALL be encoded as Unicode strings and SHOULD be limited to 150 characters. Date and time values SHALL use the RFC 3339 date-time format with UTC offset `Z` and SHALL NOT use fractional seconds.

### 2.2 Mandatory attributes

| Data Identifier | Definition | Data type | Example value |
|-----------------|------------|-----------|---------------|
| `attestation_legal_category` | Indicates the legal category of this attestation. | string | `non-qualified-EAA` |
| `gym_name` | Human-readable name of the gym or fitness provider that issued the membership. | string | `Mighty Fitness` |
| `member_id` | Unique membership identifier assigned by the issuing gym. | string | `MF-2025-001234` |
| `membership_tier` | Membership tier defining included services and benefits. | string | `Premium` |

### 2.3 Optional attributes

| Data Identifier | Definition | Data type | Example value |
|-----------------|------------|-----------|---------------|
| `member_name` | Full name of the gym member. This attribute SHOULD only be included if relying parties need to visually or legally identify the member. | string | `John Doe` |
| `member_photo` | Photograph of the member for visual verification. This attribute MAY be included only where visual verification is required. If included, it SHALL be encoded as a base64url-encoded JPEG or PNG image and SHOULD be limited to 50 KB. | string | `iVBORw0KGgo...` |
| `home_facility` | Primary facility location for the membership. | string | `Berlin - Mitte` |
| `access_facilities` | List of facilities the member can access. | array of strings | `["Berlin - Mitte", "Berlin - Kreuzberg"]` |

### 2.5 Mandatory metadata

|-----------------|------------|-----------|---------------|
| `valid_from` | Date and time from which the membership is valid, inclusive. | date-time | `2025-01-16T10:00:00Z` |

No conditional metadata is defined for this attestation type.

## 3 Attestation encoding

### 3.1 ISO/IEC 18013-5-compliant encoding

This attestation type does not support ISO/IEC 18013-5-compliant mdoc encoding in this version of the Rulebook.

This means that this Rulebook does not define an mdoc document type, mdoc namespace, CBOR encoding, or mdoc attribute mapping. Offline proximity presentation without internet connectivity is therefore out of scope for this version.

If future versions of this Rulebook require offline proximity presentation, the Rulebook author SHALL analyse whether the attestation must be issued in ISO/IEC 18013-5-compliant mdoc format and SHALL add a complete mdoc encoding section.

### 3.2 SD-JWT VC-based encoding

This attestation type supports the format specified in SD-JWT-based Verifiable Credentials (SD-JWT VC).

Attestations of this type SHALL comply with the SD-JWT VC profile specified in [HAIP], to the extent applicable for non-qualified EAA use cases in the EUDI Wallet ecosystem.

The Verifiable Credential Type (`vct`) for this attestation type SHALL be:

```text
urn:eudi:example:gym_membership_card:1
```

The `vct` value is a private name specific to this example attestation type. Production deployments SHOULD define a stable, collision-resistant `vct` value under a domain or URN namespace controlled by the relevant schema provider.

#### 3.2.1 Registered and SD-JWT VC claims

| Data Identifier | Claim name | Encoding format | Reference / Notes | Disclosable |
|-----------------|------------|-----------------|-------------------|-------------|
| `issuer` | `iss` | string | Issuer identifier. SHALL match or be resolvable to the issuer trust information described in Chapter 5. | MUST NOT |
| `subject` | `sub` | string | Subject identifier. MAY be pairwise or opaque. | MUST NOT |
| `verifiable_credential_type` | `vct` | string | Verifiable Credential Type. SHALL be `urn:eudi:example:gym_membership_card:1`. | MUST NOT |
| `issued_at` | `iat` | number | Issuance timestamp as NumericDate. | MUST NOT |
| `not_before` | `nbf` | number | Earliest validity timestamp as NumericDate. | MUST NOT |
| `expiration_time` | `exp` | number | Expiration timestamp as NumericDate. | MUST NOT |
| `confirmation` | `cnf` | object | Holder key confirmation claim for Wallet Unit key binding. | MUST NOT |
| `status` | `status` | object | Status information for revocation or suspension checks. | MUST NOT |

#### 3.2.2 Private claims specific to this attestation type

| Data Identifier | Claim name | Encoding format | Notes | Disclosable |
|-----------------|------------|-----------------|-------|-------------|
| `attestation_legal_category` | `attestation_legal_category` | string | SHALL be `non-qualified-EAA`. | MUST NOT |
| `gym_name` | `gym_name` | string | Human-readable name of issuing gym or fitness provider. | MAY |
| `member_id` | `member_id` | string | Unique membership identifier assigned by the issuing gym. | MUST |
| `membership_tier` | `membership_tier` | string | Membership tier defining included services and benefits. | MAY |
| `member_name` | `member_name` | string | Full name of the gym member. | MAY |
| `member_photo` | `member_photo` | string | Base64url-encoded JPEG or PNG image. SHOULD be limited to 50 KB. | MAY |
| `home_facility` | `home_facility` | string | Primary facility location for the membership. | MAY |
| `access_facilities` | `access_facilities` | array of strings | List of facilities the member can access. | MAY |
| `corporate_account_id` | `corporate_account_id` | string | Present only if the membership is issued under a corporate account. | MAY |
| `family_plan_id` | `family_plan_id` | string | Present only if the membership is part of a family plan. | MAY |

#### 3.2.3 Selective disclosure rules

The following claims SHALL NOT be selectively disclosable because they are needed for verification, validity evaluation, legal category evaluation, or revocation checking:

* `iss`
* `sub`
* `vct`
* `iat`
* `nbf`
* `exp`
* `cnf`
* `status`
* `attestation_legal_category`
* `valid_from`
* `valid_until`
* `cryptographically_bound_to`, if present
* `trust_anchor_hint`, if present

The following claims SHALL be selectively disclosable:

* `member_id`

The following claims MAY be selectively disclosable:

* `gym_name`
* `membership_tier`
* `member_name`
* `member_photo`
* `home_facility`
* `access_facilities`
* `corporate_account_id`
* `family_plan_id`

The intention is that a relying party can request only the claims needed for a specific purpose. For example, a partner gym may only need to verify `member_id`, `gym_name`, `membership_tier`, and `access_facilities`, while a simple discount provider may only need to verify `membership_tier` and validity.

#### 3.2.4 Example JWT claim set before SD-JWT processing

The following example is illustrative and uses placeholder values. Implementers SHALL generate real SD-JWT VCs using their own issuer keys, holder-binding keys, salts, disclosures, and status-list information.

```json
{
  "iss": "https://gym.example.com",
  "sub": "urn:uuid:7f91a4d0-7f5d-4b9a-96b0-111111111111",
  "vct": "urn:eudi:example:gym_membership_card:1",
  "iat": 1737021600,
  "nbf": 1737021600,
  "exp": 1768557600,
  "cnf": {
    "jwk": {
      "kty": "EC",
      "crv": "P-256",
      "x": "example-x-coordinate",
      "y": "example-y-coordinate"
    }
  },
  "status": {
    "status_list": {
      "idx": 42,
      "uri": "https://gym.example.com/status/1.jwt"
    }
  },
  "attestation_legal_category": "non-qualified-EAA",
  "gym_name": "Mighty Fitness",
  "member_id": "MF-2025-001234",
  "membership_tier": "Premium",
  "member_name": "John Doe",
  "home_facility": "Berlin - Mitte",
  "access_facilities": [
    "Berlin - Mitte",
    "Berlin - Kreuzberg"
  ],
  "valid_from": "2025-01-16T10:00:00Z",
  "valid_until": "2026-01-16T10:00:00Z"
}
```

In this example:

* `iat`, `nbf`, and `valid_from` refer to 2025-01-16T10:00:00Z;
* `exp` and `valid_until` refer to 2026-01-16T10:00:00Z;
* `member_id` is selectively disclosable and is expected to be disclosed when proving membership;
* `membership_tier`, `home_facility`, and `access_facilities` can be disclosed depending on the relying-party use case;
* `cnf` binds the attestation to the Wallet Unit key;
* `status` enables revocation or suspension checking.

#### 3.2.5 Example human-readable disclosure set

For access to the member's home gym, the Wallet Unit may disclose the following claims:

```json
{
  "gym_name": "Mighty Fitness",
  "member_id": "MF-2025-001234",
  "membership_tier": "Premium",
  "home_facility": "Berlin - Mitte"
}
```

For access to a partner facility, the Wallet Unit may disclose:

```json
{
  "gym_name": "Mighty Fitness",
  "member_id": "MF-2025-001234",
  "membership_tier": "Premium",
  "access_facilities": [
    "Berlin - Mitte",
    "Berlin - Kreuzberg"
  ]
}
```

For a discount-only use case, the Wallet Unit SHOULD disclose only the minimum required claims, for example:

```json
{
  "membership_tier": "Premium"
}
```

In all cases, the relying party still verifies the non-disclosable claims, issuer signature, holder binding, validity interval, legal category, and revocation status.

#### 3.2.6 Example SD-JWT VC

A full issued SD-JWT VC is not included as a normative test vector in this Rulebook because the exact value depends on issuer keys, holder-binding keys, salts, disclosures, and status-list values.

A production or conformance-test version of this Rulebook MAY include a separate test vector containing:

* the issuer public key;
* the holder-binding public key;
* the unsigned input claim set;
* disclosure salts;
* resulting disclosures;
* the issued SD-JWT VC;
* the Key Binding JWT used during presentation;
* the expected verification result.

### 3.3 W3C Verifiable Credentials Data Model-based encoding

This attestation type does not support W3C Verifiable Credentials Data Model encoding in this version of the Rulebook.

## 4 Attestation usage

### 4.1 Primary use cases

The Gym Membership Card attestation is intended for the following use cases:

* proving an active gym membership to enter a facility;
* proving eligibility for membership-tier benefits;
* proving access rights to partner facilities;
* proving eligibility for discounts or offers that depend on gym membership;
* simplifying replacement of physical membership cards.

### 4.2 PID verification

A relying party receiving this attestation does not generally need to request and verify a PID.

A relying party MAY request a PID in addition to this attestation only where identity verification is necessary and proportionate for the concrete use case. Examples may include fraud investigations, legally relevant membership transfers, or access to regulated services inside a facility.

For routine facility access, partner-facility access, or discount verification, relying parties SHOULD NOT request PID attributes if the Gym Membership Card attestation and holder binding are sufficient.

### 4.3 Relying-party verification obligations

A relying party receiving this attestation SHALL verify at least the following:

1. the SD-JWT VC issuer signature;
2. the issuer's authorization to issue this attestation type according to Chapter 5;
3. the `vct` value;
4. the `attestation_legal_category` value;
5. the validity period using `nbf`, `exp`, `valid_from`, and `valid_until` where applicable;
6. the holder binding using the `cnf` claim and the Key Binding JWT or equivalent proof required by the applicable presentation protocol;
7. the revocation or suspension status according to Chapter 6;
8. that the disclosed claims are sufficient for the declared purpose and do not exceed what is necessary.

### 4.4 Presentation protocol

This attestation is intended for online presentation using OpenID for Verifiable Presentations (OpenID4VP) and DCQL-based presentation requests.

Offline proximity presentation is out of scope for this version because this Rulebook does not define an ISO/IEC 18013-5 mdoc encoding.

### 4.5 Device binding

Attestations of this type SHALL be device-bound to the Wallet Unit key.

The attestation SHALL include a `cnf` claim or an equivalent holder-binding mechanism defined by the applicable SD-JWT VC and HAIP profile. During presentation, the Wallet Unit SHALL prove possession of the corresponding private key.

This attestation SHALL NOT be cryptographically bound to another attestation type by default.

If a specific deployment requires binding to another attestation type, such as a PID, the deployment profile SHALL define this explicitly and SHALL include the optional metadata `cryptographically_bound_to`. In that case, the value SHALL contain the attestation type or `vct` of the other attestation. For example:

```text
urn:eudi:pid:1
```

### 4.6 Transactional data

This Rulebook does not define payment use cases and does not require transactional data for strong customer authentication or electronic payments.

A relying party MAY include transaction-specific information in the presentation request, such as the name of the facility, requested benefit, or access-control context. Such transactional data SHALL NOT be embedded into the Gym Membership Card attestation itself unless defined by a future version of this Rulebook.

## 5 Trust anchors

### 5.1 Trust-anchor source

For this non-qualified EAA example, the authoritative trust-anchor information SHALL be obtained from the attestation catalogue / attestation definition in which this Rulebook is registered.

The presented attestation MAY contain a `trust_anchor_hint`, but this value is only a hint. Relying parties SHALL NOT use a trust-anchor location solely because it is asserted inside the presented attestation.

A production catalogue entry for this attestation type SHOULD define at least:

* the `vct` value;
* the trusted issuer or issuer trust list;
* the issuer public-key discovery mechanism;
* the status-list mechanism;
* the Rulebook version;
* the permitted issuer identifiers or issuer certificate constraints.

### 5.2 Example trust-anchor mechanism

For illustration, a catalogue entry may reference a JSON Web Key Set (JWKS) or signed trust list containing authorized issuers for the Gym Membership Card attestation type.

Example non-authoritative trust-list location:

```text
https://gym.example.com/.well-known/gym-membership-card-trust-list.jwks
```

A relying party SHALL verify that:

1. the trust-list location was obtained from the trusted catalogue or another trusted governance source;
2. the trust list is authentic, current, and integrity-protected;
3. the issuer identified by `iss` is authorized to issue attestations with `vct = urn:eudi:example:gym_membership_card:1`;
4. the key used to verify the SD-JWT VC is associated with the authorized issuer;
5. any issuer certificate chain, if used, is valid for the verification time and authorized for this attestation type.

### 5.3 Wallet-side issuer checks

A Wallet Unit receiving an issuance offer for this attestation type SHOULD verify that the provider is authorized to issue this attestation type before accepting the attestation, where the relevant trust information is available.

At minimum, the Wallet Unit SHOULD display the issuer identity and attestation type to the user before issuance.

## 6 Revocation

### 6.1 Revocation model

Attestations of this type are revocable.

Revocation or suspension may be necessary when:

* the gym membership is cancelled;
* the membership is suspended;
* the attestation was issued incorrectly;
* the membership was transferred or replaced;
* fraud or misuse is detected;
* the Wallet Unit or holder-binding key is reported as compromised.

### 6.2 Status mechanism

This Rulebook uses the `status` claim in the SD-JWT VC to reference a status-list mechanism.

Until a specific EUDI Wallet Technical Specification for Attestation Status Lists is mandated for this attestation type, deployments SHOULD use a status-list mechanism compatible with the applicable EUDI Wallet profile and SD-JWT VC ecosystem profile.

The following example illustrates the expected structure:

```json
{
  "status": {
    "status_list": {
      "idx": 42,
      "uri": "https://gym.example.com/status/1.jwt"
    }
  }
}
```

The concrete status-list token, status values, update frequency, caching policy, and validation rules SHALL be defined by the issuer profile or catalogue entry used in a production deployment.

### 6.3 Relying-party revocation checking

A relying party SHALL check the revocation or suspension status of the attestation before accepting it, unless an applicable ecosystem policy explicitly allows status checking to be skipped for low-risk use cases.

A relying party SHALL reject the attestation if:

* the status list cannot be obtained and the relying party's policy requires online status checking;
* the status-list signature or integrity check fails;
* the status entry indicates that the attestation is revoked or suspended;
* the status-list information is stale beyond the relying party's accepted freshness policy.

### 6.4 Wallet handling of revoked attestations

A Wallet Unit SHOULD inform the user if the attestation is known to be revoked or suspended. A Wallet Unit SHOULD prevent presentation of a revoked attestation unless the applicable wallet policy allows presentation with a clear warning.

## 7 Compliance

This Rulebook is intended to comply with the EUDI Wallet Attestation Rulebook template for a simple, non-qualified EAA example.

In particular:

* the attestation legal category is explicitly indicated as `non-qualified-EAA`;
* attributes and metadata are defined in an encoding-independent manner;
* the SD-JWT VC encoding defines a unique `vct` value;
* all top-level claims are assigned selective-disclosure requirements;
* device binding is specified;
* possible cryptographic binding to another attestation type is explicitly not required by default;
* trust-anchor retrieval is described for a non-qualified EAA;
* revocation support is defined through a `status` claim;
* relying-party obligations are defined;
* offline proximity presentation is explicitly out of scope because no mdoc encoding is defined.

This Rulebook is an example and does not itself establish a legally binding governance framework, trust framework, certification scheme, or qualified trust service.

Production deployments SHALL adapt this Rulebook to their applicable legal, security, governance, data-protection, and interoperability requirements.
